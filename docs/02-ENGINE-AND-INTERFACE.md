# Игровой движок и интерфейс

## 6. Стандартное устройство задания

У каждого задания единый и короткий интерфейс:

- Условие и ограничения.
- CSS-поле редактора.
- Живая игровая сцена.
- Раскрываемый справочник подходящих свойств и конструкций.
- Скрытая подсказка.
- Скрытое готовое решение.
- Возможность проверить результат.
- Возможность пропустить задание.
- Возможность сбросить попытку.

Правила:

- Готовое решение доступно в любой момент, но не показывается постоянно.
- Решение не должно быть спрятано за обязательным количеством ошибок или попыток.
- По нажатию решение показывается в редакторе и может применяться к сцене.
- Подсказка не должна автоматически раскрывать ответ.
- Справочник перечисляет подходящие свойства/конструкции с кратким назначением, но не подменяет решение.
- Пропуск позволяет перейти дальше; пропущенная задача остаётся доступной для возвращения.
- Не добавлять обязательный разбор после задания, многоступенчатые отчёты или сложную систему оценок.

## 7. Проверка заданий

Не разрабатывать универсальный интеллектуальный анализатор CSS и не писать собственный CSS-парсер.

Проверка должна быть небольшой и соответствовать конкретной задаче:

- CSS применяется к изолированной сцене браузером.
- Для проверки результата использовать обычные JavaScript-проверки, например computed styles, количество выбранных элементов и геометрию.
- Если задание учит конкретной конструкции, можно дополнительно проверить использование этой конструкции.
- Задачи формулировать так, чтобы корректное решение можно было проверить детерминированно.
- Ошибка применения кода не должна ломать интерфейс приложения.
- Синтаксическая ошибка не должна ошибочно считаться непониманием темы.

Не строить отдельную большую систему диагностики. Достаточно корректно показать, что задача пока не выполнена, и не мешать продолжить работу.

## 9. Интерфейс редактора

Минимально необходимое:

- Поле для обычного CSS с подсветкой синтаксиса.
- Немедленное применение к игровой сцене.
- Кнопка проверки.
- Справочник.
- Скрытая подсказка.
- Скрытое решение.
- Пропуск и сброс.

Не создавать визуальный конструктор CSS, собственный язык, сложную диагностику и дополнительные панели без конкретной необходимости.

На широком экране редактор и сцена располагаются рядом. На телефоне — переключаются или располагаются последовательно без чрезмерной прокрутки. Код должен оставаться читаемым.

## 10. Техническая архитектура

Первая версия — обычное статическое веб-приложение.

Предлагаемый стек:

- HTML, CSS и JavaScript.
- Игровые сцены внутри отдельного `iframe`.
- Пользовательский CSS применяется внутри iframe к DOM-сцене.
- Проверки выполняются JavaScript средствами браузера: computed styles, DOM и геометрия.
- Описание задач — JSON или эквивалентные простые конфигурации.
- Прогресс — `localStorage`.
- Городская графика — SVG, CSS, подготовленные изображения и лёгкие эффекты.

Изоляция iframe нужна, чтобы пользовательский CSS не ломал редактор, навигацию и оболочку приложения.

Не добавлять сервер, регистрацию или базу данных для первой версии.

```text
learning-arcade/
├── index.html
├── styles.css
├── app/
│   ├── navigation.js
│   ├── editor.js
│   ├── game-engine.js
│   ├── task-runner.js
│   └── progress.js
├── worlds/
│   ├── facade/
│   ├── structure/
│   ├── surface/
│   ├── spatial/
│   └── adaptive/
├── tasks/
│   ├── selectors.json
│   ├── flexbox.json
│   ├── grid.json
│   ├── pseudo.json
│   └── responsive.json
├── scenes/
│   ├── facade/
│   ├── construction/

│   └── lighting/

    ├── city/
    ├── buildings/
    ├── objects/

```

Это целевая логическая структура. Перед переносом существующих файлов проверить текущий прототип и сохранить рабочие части, а не создавать параллельную копию приложения.

## 11. Сохранение прогресса

Хранить только необходимое:

- текущий район;
- последнюю открытую задачу;
- выполненные задачи;
- пропущенные задачи.

Использовать локальное сохранение браузера. Регистрация, синхронизация аккаунтов и серверная аналитика не входят в первую версию.
